# Почему coding agent начинает ошибаться ещё до написания кода

Можно подключить Claude Code, Codex или Cursor, дать им доступ к репозиторию и получить технически аккуратный результат — который решает не ту задачу.

Причина часто находится не в модели и не в промпте. Она находится в исходной постановке.

Например:

> Сделать удобный и быстрый экспорт отчёта. Добавить Markdown и PDF, а также отправку по почте.

Формулировка выглядит понятной, но из неё нельзя объективно определить готовность работы:

- что именно экспортируется;
- что означает «быстрый»;
- какие данные обязательны в файле;
- входят ли PDF и почта в первый релиз;
- что происходит при ошибке записи;
- по каким критериям результат будет принят.

Coding agent не останавливается на такой неопределённости. Он заполняет пробелы наиболее вероятными предположениями. Чем больше таких пробелов, тем выше шанс получить работающий код, который придётся переделывать.

Поэтому я начал открыто разрабатывать небольшой инструмент SpecForge Gate. Он проверяет Markdown-задачу до начала реализации и без обращения к LLM ищет:

- отсутствующую цель;
- неопределённый ожидаемый результат;
- непроверяемые acceptance criteria;
- слова вроде «быстро», «удобно» и «корректно»;
- отсутствующий out-of-scope;
- пропущенные ошибки и граничные случаи;
- несколько независимых требований, склеенных в один пункт.

Первый рабочий CLI уже анализирует исходный пример и возвращает:

```text
NEEDS WORK

Errors: 3
Warnings: 3
Info: 0
```

После переработки той же задачи с измеримыми критериями, ограничениями и обработкой ошибок результат меняется на:

```text
PASS
```

Это пока только первый детерминированный слой: восемь правил, Markdown parser и отчёты в text, JSON и Markdown. Он ещё не понимает глубокие логические противоречия и может ошибаться на нестандартной структуре документа.

Следующий шаг — конфигурация правил и корпус реальных задач, на котором будем измерять ложные срабатывания. В серии покажу не только готовые функции, но и правила, которые придётся выбросить или переписать после проверки на реальных примерах.
